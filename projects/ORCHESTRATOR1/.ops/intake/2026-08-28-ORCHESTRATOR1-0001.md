This is a good first real test for the orchestrator because it is **small enough to contain**, but touches UI, persistence, secret handling, validation, and external connectivity.

I would make this change an **Integrations** module rather than just adding four configuration boxes to the existing dashboard. The important boundary is: **the portal manages integration configuration and credential references; it should not expose or persist raw secrets in normal application records.**

Paste this into the orchestrator as the new task:

3. SECRET HANDLING
==================================================

Do NOT store external credentials in plaintext in PostgreSQL.

Use credential references.

Support these credential-source concepts initially:

FILE

AWS_PROFILE

credential_reference = GITEA_TOKEN

AWS:
credential_source = AWS_PROFILE
credential_reference = ops-orchestrator

The UI may allow the administrator to enter/update a secret, but if implemented:

- write it only to the existing secure environment/secret mechanism
- never return it through the API
- never display it after save
- never write it into application logs
- never write it into Gitea project memory
- never include it in audit old/new values

If the application does not yet have a safe secret-write mechanism,
DO NOT invent an insecure one.

Instead:
- allow configuration of the credential reference
- display exact administrator instructions for setting the secret outside
  the application
- continue implementation without secret editing

### What I would expect your orchestrator to do with this

This is also a good test of the intake logic. I would expect Qwen to classify it approximately as:

> **Task type:** application feature
> **Complexity:** 2–3/5
> **Risk:** medium because credentials are involved
> **Context:** modest
> **Executor:** probably Terra because it crosses DB + API + UI + secret handling
> **Parallel agents:** 1
> **Production change:** no, unless your orchestrator itself is treated as production

And ideally it should ask you only a couple of questions if the repository doesn't answer them, especially:

* whether a secret-store mechanism already exists;
* what Gitea base URL/registry repo should be used;
* whether GitHub is actually required now or simply being made available.

That makes this a much better **orchestrator validation task** than another large feature: you'll get to see whether it can ingest a requirement, inspect its own codebase, recognize credential risk, ask targeted clarification, create the task record, route it appropriately, execute it, test it, and checkpoint the result into Gitea.
